# Stage 2 ゲート再挑戦(大規模文脈軸): 正答率は完全同点、方言単体のトークン価値は −11% — 判定「未達」とトークン価値の正確な分解

> 2026-08-19 実施。ハーネス: `experiments/stage2-context/run.mjs`(課題: `tasks.mjs`、集計: `analyze.mjs`)。
> 生データ: `results.json`(統合)、`results-haiku-q.json` / `results-haiku-mods.json` / `results-sonnet.json`

## 目的

docs/34(修正ループ軸、未達)の設計的教訓に基づく再挑戦。Tatamu の価値仮説を「書く瞬間」ではなく
「**書かれたコードがコンテキストに存在し続ける時間**」(tokens-at-rest)で測る:
コードベース全体を文脈に載せた状態での理解・変更課題において、
(a) 正答率が素の Rust と同等以上か、(b) トークン消費が有意に少ないか。

## 実験設計

- **素材**: rust2ttm 自身(5モジュール、Tatamu 1,619行 / 生成 Rust 1,680行)。実プロダクト品質・複数モジュール・自己言及的で理解課題が作りやすい
- **条件 A(ttm)**: Tatamu ルールファイル+ .ttm 全5ファイルを文脈投入
- **条件 B(rust)**: tatamuc が生成した 1:1 の .rs 全5ファイルを文脈投入(意味論同一 = 記法だけの対照)
- **理解問題 12問**: 可視性クリアの例外規則、#use 選別、コメント台帳の owner 解決、2つの行結合実装の差異(ファイル横断)、変換パイプラインの挙動予測など。全問 JSON/選択式の機械採点で、**正解は全て実バイナリの挙動で事前検証**(run 1 誤診断事故の教訓)
- **修正課題 3本**: `count` サブコマンド追加 / TODO コメントの kind 化 / 末尾ブロックコメントの tail 化。判定は「tatamuc --compile(ttm 側)→ 再ビルド → 実挙動チェック」(最大2修正ラウンド)
- モデル: Haiku 4.5 / Sonnet 5 × 各2反復、`claude -p` ヘッドレス

## 結果

### 理解問題(12問 × 2反復)

| モデル | ttm | rust |
|---|---|---|
| Sonnet 5 | **24/24** | **24/24** |
| Haiku 4.5 | **22/24** | **22/24** |

完全同点。内訳は非対称で興味深い:

- Haiku/ttm の2敗は glue-diff(最難のファイル横断問題)のみ、しかも**2敗とも「JSON のみで答えよ」の様式を破って散文回答**(内容以前の形式違反)。docs/34 の「方言の注意力税」と同型の現象が、難問でのみ顔を出す
- Haiku/rust の2敗は line-letmut / line-const — **変換パイプライン(VisClearer が可視性を消してから convert_line に渡る)の追跡ミス**。ttm 条件では 4/4 正解: 方言コードが文脈にあること自体が出力形式の理解を助けた
- Sonnet は全問正解で、方言によるハンディは検出限界以下

### 修正課題(3本 × 2反復)

| モデル | ttm | rust |
|---|---|---|
| Sonnet 5 | 6/6(全て一発) | 6/6(全て一発) |
| Haiku 4.5 | **6/6(全て一発)** | 6/6(全て一発) |

**docs/34 で観測された Haiku の方言税(+0.5 ラウンド)が消滅した。** 1,600行の実 Tatamu コードベースが文脈にあると、それ自体が few-shot 例として機能し、小型モデルでも正しい Tatamu を一発で書ける。方言税は「方言の本質コスト」ではなく「文脈に実例が無いときの初期コスト」だったことが分かる。

出力トークン(全26系列合計): Haiku ttm 61.9k vs rust 75.0k(**ttm −17%**)、Sonnet ttm 35.9k vs rust 36.6k(同等)。生成実験(docs/34、ttm が 1.7〜2倍)と逆転 — 文脈に方言実例があれば「慣れない方言を書くための思考コスト」も消える。

## トークン価値の正確な分解 — 本実験最大の成果

文脈トークンを **Claude 自身のトークナイザ**で直接測定した(従来の −13.8%/−42.2% は tiktoken=GPT系での測定だった)。

### rust2ttm 素材(1:1 生成 Rust との対照 = 方言単体の価値)

| 測定 | 文字数比 | **Claude トークン実測** |
|---|---|---|
| コード単体(.ttm vs 生成 .rs) | −26.3% | **−11.0%**(21,115 vs 23,715) |
| ルールファイル(1,639 tok)込み実質 | −19% | **−4.1%** |

### once_cell 実クレート(人間が書いた doc 豊富な Rust、2,589行)でのアブレーション

| 表現 | Claude トークン | 対 human Rust |
|---|---|---|
| 人間の Rust(doc/コメント込み) | 27,055 | — |
| コメント外部化した素の Rust(方言なし) | 11,817 | −56.3% |
| Tatamu 方言 | 10,553 | −61.0%(**対 stripped Rust −10.7%**) |
| Tatamu+サイドカー同梱 | 19,472 | −28.0% |

2つの独立素材で**方言そのものの寄与は約 −11% で頑健**。これまで方言の価値と見えていた圧縮の主役は
**コメント・doc の帯域外化**(−56%)であり、それは方言なしの素の Rust に対しても適用可能な操作である。
Claude のトークナイザは `pub fn` / `->` / `let mut` 等の Rust 定型句を効率よく圧縮するため、
それらを削る方言の利得は文字数(−26%)から大きく目減りする(−11%)。

## 判定

**ゲート未達(2軸目)。** 方言でしか表現できない価値は:

1. 理解・変更の正答率: 完全同点(改善なし。ただし**劣化もない** — 「方言は理解を損なう」懸念は棄却)
2. トークン: 方言単体で −11%(ルール分を差し引くと素材規模 24k tok で −4%、大規模化しても漸近的に −11%)— 設計原則の「**明らかに**少ないトークン消費」を満たすとは言い難い

一方で副次的発見は大きい:

- **方言税は文脈内実例で消滅する**(小型モデル含む)— 方言導入の実運用コストは従来見積りより低い
- **−28〜61% の圧縮はパイプライン(コメント外部化+サイドカー)の価値**であり、これは方言に依存しない。rust2ttm の資産(3.4M行検証済み変換器・台帳・AST パスアンカー)は「素の Rust のまま文脈圧縮する」製品にそのまま転用できる

## 次の含意

Stage 2 ゲートは修正ループ軸(docs/34)・大規模文脈軸(本書)の両方で未達。方言固有の実証済み価値は
「正答率同等のまま −11%」に留まり、圧縮の本体はコメント外部化にある。残る選択肢:

- **(a) 方言を畳む**: rust2ttm を「素の Rust 向けコメント外部化+サイドカー台帳」ツールに転回(−56% はそれだけで得られる)
- **(b) 方言を続ける**: −11% と「.ttm で書く体験」に価値を見出すなら、Stage 3(構文指向文分割)の判断材料は docs/32 に記録済み
- いずれにせよ次の実戦ドッグフーディング(ユーザー予定)が体感面の最後の判断材料になる
