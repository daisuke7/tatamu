# Stage 2 ゲート検証: 修正ループ回数の改善実測 — 判定「未達」と、その過程で得たもの

> 2026-08-18/19 実施。ハーネス: `experiments/stage2-gate/run.mjs`(課題定義: `tasks.mjs`、集計: `analyze.mjs`)。
> 生データ: `results-run1-buggy-diagnostic.json` / `results-run2-fixed-noarrow.json` / `results-run3.json` / `results-run4-final.json`

## ゲート条件と実験設計

docs/00 の Stage 2 ゲート: **「方言では表現できない価値(生成成功率や修正ループ回数の改善)が実証できること」**。

これを次の対照実験で測定した:

- **条件 A(Tatamu + Stage 2 ツール)**: ルールファイル+課題 → `.ttm` 生成 → `tatamuc --check`(構造化診断、error のみ)→ clean なら `--compile`(rustc 型検査、エラーを `.ttm` 座標の JSON で返却)→ 診断 JSON をフィードバックして修正させる
- **条件 B(素の Rust)**: 課題 → `.rs` 生成 → `rustc --emit=metadata` → **生の stderr** をフィードバック
- 課題: 初回失敗が起こり得る難度の5本(所有権を伴うグラフ枝刈り / ライフタイム付き索引 struct / 参照返し generic top-k / move クロージャ必須のパイプライン / `impl Iterator` 返し)
- モデル: Haiku 4.5 / Sonnet 5(`claude -p` ヘッドレス、stateless で毎回全文脈を渡す)
- 各 モデル×条件×課題×2反復 = 40系列/ラン。成功 = 型検査クリーン、上限4修正ラウンド

## 最終結果(run 4、クリーン測定)

| モデル | 条件 | 成功率 | 平均修正ラウンド | 一発成功 |
|---|---|---|---|---|
| Sonnet 5 | Tatamu | 10/10 | **0.00** | 10/10 |
| Sonnet 5 | Rust | 10/10 | **0.00** | 10/10 |
| Haiku 4.5 | Tatamu | 10/10 | 0.50 | 5/10 |
| Haiku 4.5 | Rust | 10/10 | **0.00** | 10/10 |

ペア比較(同一モデル×課題×反復、20ペア): Tatamu が少ない 0、Rust が少ない 5、同数 15。

**判定: ゲート未達。** フロンティア級(Sonnet)では完全同等、小型モデル(Haiku)では Tatamu 側に +0.5 ラウンドの摩擦。「改善」はどの条件でも観測されなかった。成功率も同等(改善ではない)。

### Haiku の摩擦 5件の内訳

| 件数 | 原因 | 分類 |
|---|---|---|
| 1 | `let` を書いた(規則違反 ×5箇所)— --check が全箇所を構造化指摘し1ラウンドで修正 | 方言学習コスト(ツールは正しく機能) |
| 2 | move クロージャ忘れ(課題の意図した罠)| **Rust 条件の Haiku は 2/2 で正しく書けた**のに Tatamu 条件では 2/2 で忘れた |
| 2 | 型・構文エラー | 同上の傾向(Rust 条件では発生せず) |

興味深いのは「Rust なら書けるものが Tatamu 文脈では書けない」パターン: ルールファイルへの注意配分が Rust 本来の細部(move、型)への注意を削っている可能性がある。小型モデルほどこのコストが顕著。

### トークン観測 — 価値仮説の精密化

- **成果物のコードは Tatamu が小さい**: 最終成功コードの合計(空白区切り近似)で Tatamu/Rust = 0.87(−13%、LLM 生成コード比の既知値 −13.8% と整合)
- **しかし生成時の総出力トークンは Tatamu が多い**: Sonnet 1,964 vs 1,153、Haiku 9,435 vs 4,731 — 慣れない方言を書くための思考・確認コストが、コード自体の節約を上回る
- 入力トークンも Tatamu が重い(ルールファイル分。実運用ではプロンプトキャッシュで軽減される性質)

つまり Tatamu のトークン価値は「**書く瞬間**」ではなく「**書かれたコードがコンテキストに存在し続ける時間**」に効く(大規模コードベースの読み込み・文脈保持 — まさに Stage 1 で実証した −42.2% の世界)。修正ループという「書く瞬間」の測定軸では、この価値は現れない — ゲート再挑戦は「大規模文脈での理解・変更課題」など、読む側のトークンが支配的な設定で行うべき、というのが本実験の設計的教訓。

## 最大の成果: 修正ループはツールの品質試験装置だった

ゲートは未達だが、4ランの過程で **Stage 2 ツールの実欠陥を4件検出・修正**した。これは通常のユニットテストでは見つからない種類の欠陥(「LLM が実際にどう書き、診断にどう反応するか」に依存する)で、修正ループ実験そのものが強力な QA 装置であることが分かった:

| ラン | 発見 | 修正 |
|---|---|---|
| 1 | **no-arrow 診断の誤検知**: `Fn(&T) -> K` 境界の `->`(仕様上正しい Rust-as-is)を咎め、壊れた修正案を提示。モデルは正しい初回コードを助言どおり破壊(Tatamu 平均 2.05 ラウンド、8/20 失敗が全てこれ起因)。**誤診断のある修正ループは診断なしより有害**という定量実証 | `->` 検出をシグネチャ自身の戻り位置に限定 |
| 2 | rustfmt 習慣の**複数行ビルダーチェーン**と **`where` 単独行**を tatamuc が不受理。warning 級スタイル診断でもループが回る設計 | 行頭 `.`/`where` の寛容連結受理。ループは error のみ |
| 3 | `fn … where` 折返しヘッダに `;` が付く transpile バグ。判定の過渡故障(再現しない誤陰性) | semi 規則修正。判定リトライ追加 |

run1→4 で Tatamu 側は 2.05 → 0.35 → 0.30 → 0.25 ラウンドと改善(Sonnet は 0.00 到達)。**残る差は全て Haiku の生成品質**であり、ツール起因の摩擦はゼロになった。

## 結論

1. **Stage 2 ゲート(修正ループ回数・生成成功率の改善)は未達** — フロンティアモデルで同等止まり。理由は構造的: rustc のエラー品質が既に極めて高く、`.ttm` 座標へのマッピングは「等価な情報の座標変換」であって情報量を増やさない
2. ゲート再挑戦の設計指針を得た: Tatamu の価値(存在トークンの圧縮)が効く「大規模文脈の理解・変更」軸で測るべき
3. 副産物として Stage 2 ツールの実欠陥4件を検出・修正し、「LLM 修正ループを CI 的 QA 装置として使う」方法論を確立した
