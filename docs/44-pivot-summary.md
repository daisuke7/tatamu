## 0. 一枚要約

**Tatamu 方言は自らのゲートで敗北し(精度は同点どまり、圧縮の主因は方言ではなかった)、
その測定過程で見つかった本命 —「コメント・doc を素の Rust から可逆に外部化し、必要な時だけ引く」—
に転回した。** 転回後の4日間で、可逆性(全10コーパス 231/231 バイト完全一致+CI ゲート)と、
実利(文脈 −50〜60%、フロンティアでは常駐 full を上回る精度、200k 級モデルでは fits/doesn't-fit
の分水嶺)と、限界の所在(コメントだけが担う知識と、その完全回収手段)を、すべて実測で確定した。

```
docs/34  方言ゲート敗北(修正ループ軸)      → 「価値は書く瞬間でなく、存在するコードのトークン」

docs/36  転回第一弾: strip/restore/roundtrip → 可逆コメント外部化、25ファイルで検証
```

## 1. なぜ方言を畳んだか(docs/34〜35)

Stage 2 ゲート「AI にとって Rust と同等以上の開発効率+明確なトークン削減」を2軸で実測した:

- **修正ループ軸**(docs/34): rustc エラーを .ttm 座標に写像しても、フロンティアモデルは素の Rust と
  完全同点(Sonnet 10/10 vs 10/10)。小モデルには方言の注意力税すら出た
- **大規模文脈軸**(docs/35): コードベース全体を文脈に置いた理解・修正でも完全同点。そして決定的な
  アブレーション — once_cell 27,055 tok(人間の Rust)→ **11,817(コメントを外しただけの素 Rust、−56%)**
  → 10,553(Tatamu、−61%)。**headline 圧縮の主因はコメント外部化であり、方言の寄与は −11%**
  (Claude 自身のトークナイザ実測。過去の −42% は tiktoken 測定の過大評価だった)

方言でなければならない理由が消えたため、ユーザー判断で (a)「方言を畳み、コメント外部化を素の Rust に
提供する」へ転回した。言語名 Tatamu は「コメントを畳むツール」の名として存続。

## 2. 何を作ったか(docs/36〜38、43)

**`tool/`(バイナリ `tatamu`)— 素の Rust クレート。**

- `strip`: コメント・doc をアンカー付きサイドカー台帳(`.doc.md`)へ退避。**コードは1文字も再整形しない**
  (意味安全は構成から保証)+ AST 自己検査。SAFETY コメント・非 doc ブロックコメント・intro 前の
  前書きは inline 温存
- `restore`: 台帳から完全復元。`roundtrip`: strip∘restore∘strip の不動点+バイト一致を検証するゲート
- `owners` / `show` / `notes`(lens): stripped コードを文脈に置いたまま、1項目の doc・コメントだけを
  従量取得。モジュール doc はファイル stem の疑似節、cfg 双子は `#n` シャドウで解決
- 台帳フォーマット: 物理行アンカー+スコープ owner、`above/tail/float` 種別、インデント・桁揃えデルタ
  (`above+4`/`tail+1`)、doc 前後マーカー(`^`)、形式マーカー(`~ form: block|inline`)

**硬化の過程が本体だった。** 実クレート5種(serde_core/serde_derive/regex-syntax/regex-automata/
memchr)のフルソースに掛けると、roundtrip ゲートが実世界の故障9クラスを次々検出した(cfg 双子、
多行属性、rustfmt 折返し where、enum struct 風 variant、fn ローカル item、macro_rules doc、doc 内
URL の `/*`、台帳アンカーのパース、行頭 `*self;` 誤認 — docs/38)。全修正後、最後に残った2クラス
(`/**` 形式・前書きレイアウト)も docs/43 で解消し:

> **全10コーパス・231ファイルで fixpoint 全通過+バイト完全一致 100%。既知の非一致クラスはゼロ。**
> tool/tests + GitHub Actions で常時ゲート化済み。

圧縮率はコメント密度に比例する(実測の両極: regex-automata **−62%** ↔ コメントの無い自コード −1%)。

## 3. 何が実証されたか(docs/39〜42)— 知識所在マップ

実験4本(once_cell 小規模 → memchr 10倍規模 → 改修 → 新規設計)で、「コメントを外すと何が起きるか」
を知識のクラスごとに確定した:

| 知識のクラス | 所在 | strip の影響 | 根拠 |
|---|---|---|---|
| コードに痕跡のある事実(定数・構造・アルゴリズム) | コード | **無害**(blind でも正答) | docs/39・40 |
| 実装パターンに刻まれた契約(ordering・状態機械・解放) | 隣接コード | **無害**(模倣で正しく書ける。違反検出器つき18ラン全合格) | docs/41 |
| 設計判断の why(やらない理由・作らない理由) | コメントのみ | blind で喪失 → **lens で回収** | docs/40 |
| 実装が存在しない仕様(プロトコル・規約) | コメントのみ | **blind で崩壊(11〜22%)→ lens で 100% 完全回収(=full)** | docs/42 |

副次的だが実用上大きい発見:

- **fits/doesn't-fit の分水嶺**(docs/40): コメント込み memchr はハーネス込みで Haiku の 200k 文脈に
  入らない(~205k tok)。stripped なら 80k で余裕 — 圧縮は精度以前に「扱えるか」を決める
- **lens > full**(docs/40): Sonnet は lens 11/12 vs full 10/12。コメントが「文脈にある」ことより
  「明示的に引きに行く」焦点化が効く場合がある。コストも lens が full 比 −20〜32%
- **小モデルの唯一の弱点とその解**(docs/40§6): Haiku は 80k 文脈で「引く判断」が崩壊するが、
  lens 案内を「必要なら使え」→**「まず引け(自明な時だけ省略可)」**に変えるだけで Sonnet 同点に回復。
  無駄引きは増えない(強指示は命令でなく閾値の再校正として機能する)
- **blind の危険モード**(docs/42): 仕様が見えない時、モデルは「分からない」と言わず、
  もっともらしい非互換プロトコルを確信を持って実装する

**結論: サイドカーは「失われる情報」ではなく「従量制になった情報」。** fetch-first 文言と lens が
あれば、全知識クラス・両モデル階級で full 同等以上が成立する。

## 4. 方法論の学び(実験を守った規律)

1. **不動点+バイト一致のゲートが開発を駆動した**: strip の実バグ(データ喪失級を含む十数件)は
   ほぼ全て roundtrip ゲートが検出した。CI フィクスチャも導入初日に fixpoint 破れを1件検出
2. **「full 込みで全滅したら、モデルでなく判定器を疑え」**(2回発動): コードブロック抽出の
   `/// ```` フェンス誤爆(docs/40)、ordering スキャナのヘルパ誤認(docs/41)
3. **参照解も検証対象**: c4(SWAR ループ幅)は出題者の私が間違え、モデルが正しかった(docs/40)
4. **判定器の事前 sanity**: 参照解が通り・既知の間違い実装が意図したゲートで落ちることを、
   全実験で実測してから本番を回した(docs/41 で 8/8、docs/42 で 9/9)
5. **リーク管理**: doc 由来設問は stripped 側への文言リークを走査。契約違反のフィードバックは
   正解を教えない文言に固定
