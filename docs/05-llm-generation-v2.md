# Tatamu LLM 生成実験 第2ラウンド(v0.2 仕様)結果レポート

> 2026-08-17 実施。[04-transpiler-mvp.md](04-transpiler-mvp.md) の仕様改定 v0.2 を受けた再実験。
> 生成物: `experiments/llm-generation/outputs-v2/`、集計: `check-v2.mjs`、コンパイル検証: `transpiler/compile-test.mjs`

## 目的

v0.2 仕様(束縛時型注釈 `x: Type := expr`、`if let` 許容、必要箇所のターボフィッシュ許容)を few-shot プロンプトに反映し、**実際のコンパイル通過率**で生成成功率を測る。第1ラウンドとの違いは、評価がレビュー判定ではなく rustc による実測になったこと。

## 方法

第1ラウンドと同一の4モデル(Haiku 4.5 / Sonnet 5 / Opus 5 / Fable 5)・同一6課題。プロンプトの仕様を v0.2 に更新し、生成 → `tatamuc` で変換 → `rustc --emit=metadata` で型検査。対照群(素の Rust)は第1ラウンドの 24/24 コンパイル成功を使用。

## 結果: 24/24 コンパイル成功・全モデル違反ゼロ

| モデル | コンパイル(第1R→第2R) | 規則違反(第1R→第2R) | トークン削減 vs Rust |
|---|---|---|---:|
| Fable 5 | 4/6 → **6/6** | 0 → 0 | 32.9% |
| Opus 5 | 4/6 → **6/6** | 0(意味欠陥1)→ 0 | 35.3% |
| Sonnet 5 | 4/6 → **6/6** | 0 → 0 | **45.1%** |
| Haiku 4.5 | 6/6* → **6/6** | **37 → 0** | 27.1% |

\* 第1ラウンドの Haiku は「違反のターボフィッシュ」が偶然型注釈として機能してコンパイルは通っていた。

### 特筆事項

1. **修正ループが不要だった。** エラーフィードバックによる修復実験を予定していたが、全24本が一発でコンパイル通過し、修復対象が存在しなかった。
2. **Haiku の違反 37 → 0。** v0.1 で Haiku が Rust の習慣(行末 `;`、ターボフィッシュ)に引き戻されていた問題は、v0.2 が「Rust が要求する箇所では注釈を書く」と Rust の習慣に沿う方向に仕様を寄せたことでほぼ消滅した。**弱いモデルへの対策は「規則を増やす」より「母体言語の直感に沿わせる」が正解**という設計知見。
3. **第1ラウンドで Opus に出た推敲残しバグも今回は発生せず**(偶然の可能性もあるためサンプル数の限界は変わらず)。
4. トークン削減は 27〜45% を維持。注釈のコストは Haiku で最も重い(35.2%→27.1%)が、これは Haiku が `Vec<_>` 注釈を必要以上に書いたため。それでも 27% 削減。

## Stage 1 ゲート条件: 最終判定

| 条件 | 判定 |
|---|---|
| トークン削減 30% 以上 | ✅ 生成コード比 27〜45%(中央値 34%)、実コード外挿 44〜46% |
| 生成成功率が素の Rust と同等 | ✅ **コンパイル実測で Tatamu 24/24 = Rust 24/24** |

**Stage 1 ゲートはコンパイル実測ベースで正式にクリア。**

## 制約(継続)

- 各セル1サンプル・小規模6課題。統計的主張には課題数・試行数の拡大が必要
- 被験者は Claude ファミリーのみ。他社モデル(GPT / Gemini)での転移は未検証
- 課題が「few-shot 例と同ジャンルの小さな CLI プログラム」に留まる。ジェネリクス・ライフタイム・async・複数ファイルは未踏

## 次のステップ(Stage 2 へ)

1. **難課題での限界測定** — ジェネリクス・ライフタイム・トレイト境界・async を含む課題セットで同じパイプラインを回し、v0.2 仕様の穴を洗い出す
2. **診断の実装** — 不正 Tatamu への修正提案つき構造化エラー(第1R の Opus バグのような入力を検出)。「生成→変換→コンパイル→フィードバック」パイプラインは今回の 24/24 で不要だったが、難課題では必要になるはず
3. **cargo プロジェクト対応** — 単一ファイル → 複数ファイル+依存クレート(prelude マップの拡張、Cargo.toml 生成)
4. **ドキュメントのアウトオブバンド化の設計** — 実コード外挿 44〜46% の前提であるコメント分離の仕様化(01 レポートの示唆 3)
