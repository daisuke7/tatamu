# 第2回ドッグフーディング レポート: mdlite(256行・テスト付き)

> 2026-08-18 実施。ソース: `dogfood/mdlite/src-ttm/`(block / inline / render / tests / main の5モジュール)

## 題材

**mdlite** — Markdown サブセット → HTML 変換 CLI。見出し・段落(行結合)・順序付き/なしリスト・引用(行マージ)・フェンスコードブロック・水平線と、インライン装飾(bold / em / code / リンク・未クローズは literal・全域エスケープ)を実装。**ユニットテスト12本付き、256行(非空行)** — 第1回(47行)の約5倍のスケール。

## ワークフローの記録

1. `--check`: 5ファイル中4ファイル診断ゼロ。tests.ttm で誤検知1件 → **摩擦 #1**
2. `--compile`: **型検査は一発 ok**(256行・データ enum・Peekable・ライフタイム付きヘルパ込みで、筆者の Tatamu 側の型エラーはゼロ)。ただし警告1件 → **摩擦 #2**
3. `cargo test`: **12/12 一発通過**。デモ文書の変換も正しい HTML を出力

| # | 摩擦 | 種別 | 対処 |
|---|---|---|---|
| 1 | `--check` が**文字列リテラル内の** `let x = 1;`(テストの期待値)に no-let-binding を誤検知 | 診断のバグ | 診断前に文字列内容を潰すよう修正 |
| 2 | テストモジュールへの自動注入 `use crate::…::*` が非テストビルドで unused 警告 | プロジェクト生成の質 | `#[test]` を含むモジュールに `#![allow(unused_imports)]` を注入 |

前回に続き、**筆者が書いた Tatamu 自体の誤りはゼロ**。摩擦は両方ツール側で、その場で修正・回帰なし。テスト(`#[test]` 属性・`assert_eq!`)は「Rust のまま」領域として仕様追加なしで機能し、クロスモジュール解決がテストモジュールにもそのまま効いた。

## トークン実測: 3者比較(今回の核心)

同一仕様・同等機能・テスト付きで:

| 対象 | トークン(o200k) | 行数 | Tatamu 比 |
|---|---:|---:|---|
| **Tatamu(.ttm 5ファイル)** | **2,075** | 256 | — |
| 生成 Rust(機械展開・コメントなし) | 2,408 | 269 | Tatamu が **−13.8%** |
| **最初から Rust で書いたコード**(Sonnet 5 が同一仕様から自然に執筆、17テスト通過を検証済み) | **3,593** | 393 | Tatamu が **−42.2%** |

- 「最初から Rust」版は idiomatic な実物: doc コメント、rustfmt の縦長整形、`use` 文、`#[cfg(test)] mod tests` 定型、`pub`、丁寧なヘルパ分割を自然に含む。**−42.2% は 01/02 実験からの外挿(44〜46%)とほぼ一致**し、紙上の見積もりが実プロジェクトで再現された
- 生成 Rust との差(13.8%)が「純粋な文法圧縮」、from-scratch との差(42.2%)が「文法圧縮+書式・コメント・定型文の排除」の合算 — 差分の大半は 01 で特定した「コメントと書式」であり、アウトオブバンド設計(09)が効いている
- 公平性の注記: Rust 版はテストが5本多い(17 vs 12)。テスト規模を揃えた概算補正でも 40% 前後の差は維持される

## 判定

**合格。** 256行・テスト付きのスケールでも、(1) 開発ループは .ttm 座標系で完結し型エラーゼロ、(2) テストという新しい利用形態が仕様追加なしで動き、(3) ユーザー設定の2大要件 — 「AI にとって Rust と同等以上の開発効率」(摩擦2件は共にツール側・即修正)と「Rust より明らかに少ないトークン」(**対実書き Rust −42.2%**)— を実プロジェクトで同時に満たした。
