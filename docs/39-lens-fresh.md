# fresh-context 実験: stripped コード+lens 従量参照は「必要な時だけ、正しく引き、精度を落とさない」

> 2026-08-20 実施。docs/35 の懸念③(サイドカー参照頻度)への直接実験。
> ハーネス: `experiments/lens-fresh/`(run.mjs / tasks.mjs / analyze.mjs / sanity.mjs)。

## 1. 設計

**問い**: コメント・doc を外部化したコードだけを新しい文脈に渡された AI は、(1) 精度を保てるか、
(2) サイドカーをどれくらい・どんな時に引きに行くか、(3) 引きすぎて削減分を食い潰さないか。

- 対象: once_cell フルソース(5ファイル、doc 密度最高クラス、strip −56%)
- 条件:
  - **stripped**: 外部化済みコードを文脈に常駐+`./notes <name>`・`./owners`(実体は `tatamu notes/owners`、
    呼び出しをログ)を Bash ツールとして許可(`claude -p` agentic、他コマンドは不許可)
  - **full**: コメント込み原文を文脈に常駐、ツール無し(従来型)
- 課題:
  - 理解 12 問(4択・機械採点)。**doc 問 8**(正解が外部化されたコメント・doc にしか無い:
    atomic ordering の選定理由、`T: Send` が要る理由、MSRV ポリシー、`const` Lazy の罠 等)+
    **コード問 4**(コードから導出可能:状態定数の値、内部表現 等)
  - 改修 2 課題(race.rs に `is_initialized` ×4型 / `OnceBox::into_inner`(Drop 併存で二重解放を
    避ける必要あり))。ビルド+挙動フィクスチャで判定、最大2回の修正ラウンド。
    判定器は事前に健全性検証(参照解が通り、未改修が落ちる)
- モデル: Haiku 4.5 / Sonnet 5(方針どおり Opus 以下)

準備中に lens の実ギャップを1件発見・修正: モジュールレベル doc(`//!`)がサイドカーの intro 領域に
あり `notes` で取得不能だった → ファイル stem を疑似 owner とする節として公開(`./notes race`)。

## 2. 結果

### 正答率 — 全条件パーフェクト

| | stripped | full |
|---|---|---|
| Haiku(doc 8 問 / コード 4 問) | 8/8・4/4 | 8/8・4/4 |
| Sonnet(同) | 8/8・4/4 | 8/8・4/4 |
| 改修(2課題) | 4/4 一発成功 | 4/4 一発成功 |

### 参照頻度 — 選別がほぼ理想的

- **doc 問**: 16 件中 9 件で `./notes` を実行(計 16 回、平均 1.6 ターン)。引き先も的確
  (`notes race` でモジュール doc、`notes lib`、`notes Sync for OnceCell` 等)
- **コード問**: **8 件中 0 件** — 無駄引きゼロ。「コードで分かることは引かない」が両モデルで成立
- doc 問で引かずに正解した 7 件は、4択の選択肢制約+コードからの推論で到達(選択肢無しの
  自由記述ならもっと引くはず — 保守的な下限と解釈)
- 改修中の参照は Sonnet が 1 課題で 4 回(`is_initialized` 追加時に既存 API の doc を確認)、他はゼロ

### トークン・コスト — 引いても stripped が安い

質問フェーズ(12 問合計、ツール往復込み):

| | stripped | full |
|---|---|---|
| Haiku | **$1.05** | $1.37 |
| Sonnet | **$4.30** | $5.44 |

文脈が −56% 小さい効果が、notes 往復の追加コストを吸収してなお **約2割安**。
改修の出力トークンも stripped 5.6〜6.3k vs full 6.1〜9.3k — コメント込み全文の書き戻しは出力側でも重い。

## 3. ハーネスの罠(2件、full 条件のみ発症)

full 条件の改修が最初「4戦全敗」に見えたが、両方ともハーネスのバグだった:

1. コードブロック抽出が「最後のブロック」を取っており、長出力の断片を掴んだ → 最大ブロックに変更
2. **doc コメント内の ```` ``` ```` フェンス**(`/// ```` の例示コード)で正規表現の終端が誤爆し、
   全文が約350行で切れていた → 行頭 ``` のみを終端に

修正後は full も 4/4。教訓として面白いのは、**この事故はコメント込み出力にしか起きない**こと —
stripped なコードはツール連鎖・機械処理に対しても頑健というおまけの観察。

## 4. 判定

**懸念③は解消。** 精度低下なし、参照は必要時のみ・的確、コストは常駐分の削減が支配的で従量参照込みでも
full より安い。docs/36-38 の可逆性保証と合わせ、(a) パス(素 Rust+コメント外部化+lens)の
中核仮説「読みは安く、why は必要な時だけ」は once_cell 規模では実測で成立した。

限界と次の候補:
- 4択形式は「引かなくても当たる」方向のバイアスがある(自由記述・実バグ修正でより厳しく測れる)
- once_cell は1クレート・5ファイル。多クレート・大規模文脈での再現、および「サイドカーの存在を
  教えない」ブラインド条件は未測定
- 改修課題はコメント知識が必須ではなかった(SAFETY 級の知識が正否を分ける課題設計が次の一手)

コスト: 有効データ $13.8+破棄ラン $5.8 ≈ **$19.6**。
