# Tatamu LLM 生成実験 結果レポート

> 2026-08-17 実施。[02-paper-prototype.md](02-paper-prototype.md) の「次のステップ 1」に対応。
> 実験コード: `experiments/llm-generation/`(`prompt-tatamu.md`, `tasks.md`, `check.mjs`, 生成物は `outputs/`, 生データは `results.json`)

## 目的

ゲート条件の後半「LLM の生成成功率が素の Rust と同等以上」を検証する。few-shot だけで LLM が Tatamu を正しく書けるか(= リスク①「学習データゼロ問題」の対策 (c) が機能するか)を測る。

## 方法

- **被験者**: 会話文脈を持たない新規エージェント 8 体(Claude Haiku 4.5 / Sonnet 5 / Opus 5 / Fable 5 × 2 条件)
- **条件 A(Tatamu)**: v0 ルール仕様 + 例3本(wordcount / config_parse / geometry)のみを与えて生成
- **条件 B(Rust、対照)**: タスクのみ与えて idiomatic Rust を生成
- **課題**: few-shot 例とは別の新規 6 課題(anagram / csvavg / inventory / dedup / fib / rpn)
- **評価**: (a) 文法準拠 — ルール別ヒューリスティックチェッカー(`check.mjs`)+手動レビュー、(b) 意味 — レビュー判定(コンパイラ不在のため)、(c) トークン数 — o200k

## 結果 1: 文法準拠率

機械チェックによるルール違反数(6課題合計):

| モデル | 違反数 | 準拠プログラム | 内訳 |
|---|---:|---:|---|
| Fable 5 | **0** | 6/6 | — |
| Opus 5 | **0** | 6/6 | (ただし手動レビューで rpn に欠陥1件、下記) |
| Sonnet 5 | **0** | 6/6 | — |
| Haiku 4.5 | **37** | 0/6 | 行末 `;` 残存 ×約27、ターボフィッシュ残存 ×6 など |

- **フロンティアモデル(Sonnet 以上)は few-shot だけでほぼ完全な Tatamu を書いた。** 学習データゼロ問題は「仕様+例をコンテキスト常駐」で回避可能という 00-concept の仮説 (c) を実証。
- **Haiku は Rust の習慣に引き戻される**(文末セミコロン、`::<Vec<_>>`)。ただし違反は全て機械検出可能かつ機械修正可能(セミコロン除去・ターボフィッシュ削除)であり、トランスパイラのエラーフィードバックか自動整形で吸収できる種類。
- 意味面の欠陥は 1 件のみ: Opus の rpn に `mut stack = Vec::new()` と `mut stack := Vec::new()` の重複行(推敲の消し忘れ様の欠陥)。他 23 プログラムはレビューで意味的に妥当と判定。

## 結果 2: 仕様の穴が見つかった(実験の副産物)

Opus / Sonnet / Haiku が `if let Some(x) = ...` を使用し、当初チェッカーが「`let` 禁止」違反と誤判定した。**v0 仕様は束縛の `let` を廃止したが、パターンマッチ構文 `if let` / `while let` の扱いを未定義にしていた。**

→ **v0.1 明確化**: `if let` / `while let` はパターンマッチ構文として許容(S1 は文としての `let` 束縛のみ禁止)。チェッカーにも反映済み。

## 結果 3: 生成コードのトークン数

同一モデル・同一課題の生成物同士の比較(6課題合計、o200k):

| モデル | Tatamu | Rust | 削減率 |
|---|---:|---:|---:|
| Fable 5 | 762 | 1174 | **35.1%** |
| Haiku 4.5 | 804 | 1240 | 35.2% |
| Opus 5 | 823 | 1275 | 35.5% |
| Sonnet 5 | 762 | 1389 | **45.1%** |

紙上プロトタイプ(27.6%)より大きい削減になった。生成 Rust には引数チェックの定型文・冗長なフォーマット・コメントが自然に含まれるため、「LLM が実際に吐くコード」同士の比較では書式レイヤの効果も乗るからである。**この 35〜45% が実運用に近い削減率と考えられる。**

## ゲート条件の評価(Stage 1)

| 条件 | 判定 |
|---|---|
| トークン削減 30% 以上 | ✅ 生成コード比 35〜45%(紙上比でも実コード外挿 44〜46%) |
| 生成成功率が素の Rust と同等以上 | ✅(暫定)フロンティアモデルで準拠 6/6、意味欠陥は 24 本中 1 件 |

**Stage 1 のゲートは暫定クリア。** トランスパイラ実装に進む価値がある。

## 制約

- 各セル 1 サンプルのみ(統計的検定なし)。課題も小規模 6 本
- コンパイル検証なし(Rust ツールチェーン不在)。意味判定はレビューによる
- 被験者が全て Claude ファミリー。GPT / Gemini 系での転移は未検証(API アクセスが必要)
- 意味判定者(Fable)と被験者の 1 体が同一モデルであるバイアス

## 次のステップ

1. **Stage 1 トランスパイラ(Tatamu → Rust)の最小実装** — ゲート暫定クリアにより着手判断
2. トランスパイラ完成後、生成 Tatamu を実際にコンパイル・実行して意味正しさを自動判定する再実験(レビュー判定の置き換え)
3. Haiku 級モデル向けの自動整形(セミコロン・ターボフィッシュ除去)をトランスパイラの寛容モードとして仕様化するか検討
4. 他社モデルでの転移検証(API アクセス確保後)
