## パターン極端系(今回)の要点

質のストレステストとして選んだ6クレートのうち、**rayon・itertools・rand は初見で無修正 100%**。イテレータアダプタのジェネリクス連鎖・トレイト実装の物量は、それまでの規則獲得で既に汎化されていた。残りが教えてくれたもの:

| 発見 | 対処 |
|---|---|
| **`R<T>` エイリアスとユーザー定義 `R` 型の衝突**。bevy がテストで `struct R<const I: usize>` を定義しており、`Res<R<3>>` が `Res<Result<3, Box<dyn Error>>>` に展開されて型が壊れた | ファイル内に `struct/enum/type/union/trait R` または `as R` を検出したら expandR を自動無効化。**Tatamu 仕様の予約識別子リスクが実クレートで顕在化した初のケース**で、言語設計へのフィードバックとして最重要 |
| `impl<R> FnRet for fn() -> R {` — fn ポインタ型を含む impl ヘッダが「値を返す fn」と誤判定され、中の `type Output = R` が tail 式扱い | fn 文脈判定に「fn の後に識別子」を要求 |
| `.0 .0`(ネストタプルアクセス)vs float トークン化 — `x.0.0` はトークン列として `x` `.` `0.0`(float)にも `x` `.` `0` `.` `0` にも読め、印字経路で揺れる | compare のマクロトークン正規化で float リテラル `N.N` を `N` `.` `N` に分解し曖昧性を消去 |
| 式ポジションの turbofish `Path::<T>` と型ポジションの `Path<T>` の差 | AST 比較用に colon2 を正規化 |
| diesel の再帰 macro_rules 群で、マクロ呼び出し closer の `;` 復帰が本体内で誤発火 | macro_rules 本体はアイテム変換・semi 復帰とも完全 verbatim に統一 |
| thiserror の属性トークン `#[error("…", f = .1)]` の spacing 差、旧 2015 スタイル `Box<Any>`(dyn なし) | 属性トークンにも spacing/末尾カンマ正規化、trait object の dyn を統一 |

## 未解決2件の詳細と、対応を打ち切る根拠

### 1. rust-analyzer `crates/test-utils/src/minicore.rs`(convert-fail)

**状況**: syn(Rust 公式パーサライブラリ、v2.0.119)が**パース自体に失敗**する。原因は2つの nightly 限定構文:

- **macros 2.0(`decl_macro` feature)が22箇所**: `pub macro Copy($item:item) {}`、`pub macro offset_of(...)` など。`macro name {…}` 宣言は現在も nightly でしか書けず、syn は未サポート
- **`builtin #` 構文**: `{builtin # offset_of($Container, $($fields)+)}` — rustc 内部の builtin マクロ構文

このファイルは rust-analyzer が**テスト内で std の代替として注入する疑似 core ライブラリ**(`#[lang = "…"]` アイテムの束)であり、意図的に rustc 内部構文で書かれた特殊フィクスチャ。

**打ち切りの根拠**:
1. rust2ttm のアーキテクチャは「syn = 構造の真実」を前提とする(docs/30)。syn が読めない入力への対応は、rustc 内部パーサへの乗り換えを意味し、PoC の範囲を大きく超える
2. Tatamu のユースケース仮説「Rust 大規模プロジェクトの AI 開発効率化」の対象は stable Rust のプロダクトコードであり、nightly 内部構文のテストフィクスチャは対象外
3. 失敗モードは convert-fail(明示的エラーで停止)。**静かな破壊は起きない**ため、運用上は「このファイルを変換対象から除外」で完結する
4. 参考: 同種のフィクスチャ(rust-analyzer の parser/test_data — 意図的に壊れた Rust)は測定ハーネス側で除外済み。minicore は「壊れてはいないが nightly」という中間的存在のため測定に残し、限界の記録として扱う

### 2. polars `crates/polars-io/src/path_utils/mod.rs`(regen-parse-fail)

**状況**: このファイルには **`&&` の右オペランドとしてのブロック式**(block-in-condition)が2箇所ある:

```rust
// L211: fn の tail 式内
paths.len() == 1 && !has_glob(...)
    // And isn't a file
    && {
        ( /* コメント行・括弧折返しを含む複数行 */ )
        || ( ... )
    }

// L300: if の条件内(さらに難しい)
let out = if !path_str.ends_with("/") && (...) && {
        // 4行のコメント
        path.has_scheme() || path.as_std_path().is_file()
    } {          // ← 条件ブロックの閉じと if 本体の開きが並ぶ
        ...
```

行ベースの文結合(join)は「`{` で終わる行 = ブロック開始 = 文の区切り」を基本仮定としており、この構文はその仮定の真裏を突く: `{` が**式の途中**に現れ、さらに L300 では `} {`(条件ブロック閉じ+本体開き)という「閉じたのに文が終わらない」並びが続く。

**打ち切りの根拠**:
1. **部分対応は実施済みで、それでも残る形だから**。`&& {` / `|| {` 終端の継続、`} {` 先読み継続、ブロック内コメントの flush 抑止まで実装し、L300 系の単純形は通るようになった。残るのはコメント行・括弧折返し・`||` 分割が複合した形で、これを通すヒューリスティックを追加するたびに**他クレートで退行が発生した**(実測: `} {` の無条件継続で polars 自体が 99.6%→99.4% に退行)。局所ヒューリスティックの限界点に達している
2. **頻度が極端に低い**。340万行・7,900ファイル中この1ファイルのみ。この構文には `clippy::blocks_in_conditions` という専用 lint が存在するほど非慣用的で、多くのプロジェクトでは CI で弾かれる書き方
3. **失敗は検出可能**。regen-parse-fail として明示的に停止し、静かな破壊ではない。運用上は「該当ファイルのみ手修正(条件を変数に括り出す1行の変更で解消)または変換対象外」で対処できる
4. 根本解決の正道は行ベース join の廃止(= 文分割も syn の Stmt 境界から得る設計変更)であり、これは「Stage 3(自前 AST/構文指向処理)への移行」という既存の設計判断事項に属する。1ファイルのためにヒューリスティックを重ねるより、移行判断の材料として記録する方が価値が高い

## 結論

- 同値ゲート駆動の「測定→分類→修正」ループは、340万行スケールで**実質 100%**(除外は入力側限界2件)まで到達した
- 途中で発見・修正した**意味破壊級**(raw string 内容変化、derive 喪失、文字列内変換、trailing space 喪失など十数件)はすべて compare ゲートが検出したもので、このゲートなしの転写ツールは信頼できない、という設計上の教訓が確定した
- 残る2件は「変換器の能力不足」ではなく「入力が stable Rust でない」「行ベース設計の既知の限界(Stage 3 判断材料)」として分類・記録済み。**現行アーキテクチャでの改善対象は尽きた**
