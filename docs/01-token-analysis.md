# トークン実測実験 結果レポート

> 2026-08-17 実施。[00-concept.md](00-concept.md) の「検討手順 2: トークン実測実験」に対応。
> 実験コード: `experiments/token-analysis/`(`analyze.mjs`, `variants.mjs`、生データは `results.json`, `variants.json`)

## 実験概要

- **サンプル**: ripgrep / serde / clap の3リポジトリから、テスト・example を除く 2〜60KB の実 Rust コード各30ファイル、計 **90ファイル(約1.1MB)**
- **トークナイザ**:
  - `o200k_base`(GPT-4o 系、`gpt-tokenizer` npm パッケージ)
  - `claude_legacy`(`@anthropic-ai/tokenizer` npm パッケージ = Claude 2 世代。**現行 Claude のトークナイザは非公開のため、あくまで近似**)
- **手法**: 自前の簡易 Rust レキサでソースを文字カテゴリ(キーワード/識別子/記号/空白/コメント/文字列/数値)に分類し、BPE トークン列とオフセットを突き合わせて各トークンのコストをカテゴリに按分帰属(o200k は 90ファイル全てで round-trip 一致を確認)

## 結果 1: トークンはどこに消えているか

ベースライン: **o200k で 23.7 トークン/100文字**(claude_legacy は 27.1)。

カテゴリ別シェア(o200k、全体 264,843 トークン):

| カテゴリ | シェア | 補足 |
|---|---:|---|
| 識別子 | **26.8%** | 最大の消費源。1出現あたり平均 1.34 トークン |
| コメント | **21.9%** | リポジトリ差が大きい(ripgrep 29.7% / serde 11.9%) |
| 空白 | **21.5%** | ほぼインデント由来 |
| 記号・区切り | **18.9%** | `::` `->` `{}` `;` など |
| キーワード | **4.6%** | 1出現あたり平均 **0.81 トークン**(隣接空白と融合して 1 トークン未満) |
| 文字列リテラル | 6.1% | |
| 数値 | 0.3% | |

行タイプ別では: コメント行 23.6%、属性(`#[...]`)3.1%、閉じ括弧だけの行 3.3%、import/mod 行 **1.9%**。

## 結果 2: 機械的変換でどれだけ削れるか

同一コードへの変換のみでの削減率:

| 変換 | o200k | claude_legacy |
|---|---:|---:|
| インデント除去 | 10.2% | **−0.6%(悪化)** |
| インデントをタブ化 | −1.6%(悪化) | −8.1%(悪化) |
| コメント除去(+空行除去) | 24.8% | 23.9% |
| ミニファイ(コメント+インデント+空行除去) | **33.1%** | 23.9% |
| ミニファイ+改行を空白に置換 | 33.1% | **31.9%** |

## 結果 3: 記号置換は逆効果

| 表記 | o200k | claude_legacy |
|---|---:|---:|
| `fn ` | 2 | 2 |
| `ƒ `(置換案) | 2 | 3 |
| `<T>` | 2 | 3 |
| `⟨T⟩`(置換案) | **7** | **7** |
| `->` / `=>` / `::` | 各1 | 各1 |

コンセプト時の懸念(リスク②)が実証された: **「短い文字列 = 少ないトークン」は成り立たない。** キーワードは既に実質1トークン未満であり、Unicode 記号への置換は最大3倍以上高くつく。

## 設計への示唆

1. **キーワード短縮・記号発明は捨てる。** キーワードは全体の 4.6% しかなく、既にほぼ最安。文法は ASCII・既存キーワード維持が正解。
2. **最大のレバーは「フォーマット」と「識別子」。** ミニファイだけで o200k 33% 削減 — Stage 1 のゲート条件(30%)は書式ポリシーだけでほぼ到達できる。つまり方言の本丸は文法記号ではなく、(a) インデント・改行に意味を持たせない/持たせるの設計、(b) 識別子の繰り返しを減らす言語機能(型推論の徹底、メソッドチェーン、暗黙 self、短い標準ライブラリ名)。
3. **コメントの扱いが戦略上の分岐点。** トークンの約22%がコメント。ただし AI がコードを理解・修正する際の文脈価値があるため、単純除去ではなく「ドキュメントをアウトオブバンド化する(別ファイル/別チャネルに置き、コンテキストに入れるかを選択可能にする)」設計が有望。
4. **トークナイザ依存性が現実に存在する。** インデント除去は o200k で +10.2%、claude_legacy では −0.6% と正反対。特定トークナイザに過剰最適化せず、複数トークナイザでの平均改善を設計目標にすべき。タブインデントは両方で悪化するので禁止。
5. **import 自動化の削減効果は小さい**(1.9%)。DX 改善(LLM が import を間違えない)としての価値はあるが、トークン節約策としては優先度低。

## 制約・注意

- claude_legacy は Claude 2 世代のトークナイザで、現行モデルの実コストとは異なる可能性がある
- サンプルは有名 OSS 3つに偏っており、コメント率などプロジェクト差が大きい(削減率のレンジとして解釈すべき)
- 識別子・キーワードのコストは按分帰属による近似値

## 次のステップ(検討手順 3: 紙上文法プロトタイプ)

本結果に基づき、方言の設計仮説は次の3本柱に絞る:

1. **書式レイヤ**: コメント・インデントのアウトオブバンド化(表示時に復元、トークン化時は最小形)
2. **識別子レイヤ**: 型推論の徹底・繰り返し排除で識別子出現を削る文法
3. **記号レイヤ**: `{}` `;` などの区切り最小化(ただし空白との融合を実測しながら)

同一プログラムを「素の Rust」と「方言」で書き比べ、トークン数と LLM 生成成功率を測るのが次の実験。
