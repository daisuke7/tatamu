# Stage 2-4: ドキュメントのアウトオブバンド化 設計 + 最小実装

> 2026-08-17 実施。`tatamuc --docs <file.doc.md> <file.ttm>` として最小実装済み。

## 背景

[01-token-analysis.md](01-token-analysis.md) で実コードのトークンの **21.9% がコメント**と判明。実コード外挿 44〜46% 削減(02)の前提は「コメントをコードから分離する」ことであり、その設計が Tatamu の成否を握る(01 の示唆 3)。

## 設計

### 原則: コードとドキュメントを別ファイル・別ライフサイクルにする

- `.ttm` は**常にコメントゼロ**。LLM のコンテキストには原則こちらだけが入る
- ドキュメントはサイドカー `<name>.doc.md` に置く。**必要なタスクのときだけ**コンテキストに載せる(ツール/エージェント側の判断)
- 展開(`tatamuc --docs`)で Rust の `//!` / `///` doc コメントとして再結合 — rustdoc・人間のレビュー・docs.rs 互換

### サイドカー形式

```markdown
# <モジュール概要>          ← //! モジュールドキュメントになる

## <item名>                ← その名前の fn/struct/enum/trait/const に付く
<本文>                     ← /// doc コメントになる
```

### 最重要の設計判断: 行番号ではなく項目名でアンカーする

コメントを行番号で紐付けると、コードの編集(= LLM の主活動)のたびにズレて壊れる。**項目名(fn / struct / enum / trait / const の識別子)でアンカー**することで、コード側をいくら編集してもドキュメントの対応が保たれる。diff も小さくなる(01 の「AI 寄り」定義のうち「局所編集のしやすさ」に合致)。

### トークン経済

| モード | コンテキストに入るもの | コメント分のコスト |
|---|---|---|
| 通常の編集・生成 | `.ttm` のみ | **0** |
| 仕様理解が必要なタスク | `.ttm` + 該当 `.doc.md` | 必要な分だけ |
| 人間のレビュー / 公開 | 展開された Rust(docs 込み) | LLM は通らない |

インラインコメント方式では全タスクが常時 22% を払うのに対し、サイドカー方式は「払うかどうかをタスク単位で選べる」。

## 実装(最小)

`mergeDocs(rust, sidecarMd)` を実装。挙動:

- 冒頭本文 → `//!`、`## name` 節 → 該当項目の直上に `///`(`#[derive]` 属性より上に配置)
- インデントは項目に合わせる。同名の最初の項目のみに付与

検証: `config_parse.ttm` + `config_parse.doc.md` → 展開 Rust が意図どおりの位置に `//!` / `///` を持ち、**rustc コンパイル成功**。既存29本の回帰テストも通過。

## 未決事項(次の設計課題)

1. **doc の鮮度管理** — コードと doc の乖離を検出する仕組み(項目の増減チェック、CI で「doc なし項目」を警告するか)
2. impl ブロック内メソッド単位のアンカー(現状はトップレベル項目のみ。`## Type::method` 記法の予約が候補)
3. 逆方向(既存 Rust のコメント → サイドカー抽出)— Rust コードベースの Tatamu 移行ツールとして価値がある
4. `.doc.md` 自体を LLM に書かせる/更新させるワークフローの実験
