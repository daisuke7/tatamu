# Tatamu — AI寄りプログラミング言語 構想ドキュメント

> 2026-08-17 時点。Claude チャットでの初期議論を整理したもの。

## 言語名: Tatamu(畳む)— 仮称

2026-08-17 決定(仮称)。動詞「畳む」に由来 — **畳んで小さくするが、広げれば元の形に戻る**。Stage 1 の設計(母体言語へ機械的に展開できる短縮記法レイヤー)を正確に表すメタファー。

- トークンコストは o200k / claude_legacy とも 2(キーワードではなくツール名・拡張子程度の頻度なので実用上問題なし)
- 日本語として完全に読める。tatami の連想で国際的にも発音しやすい
- crates.io / npm とも空きを確認済み(2026-08-17)
- 命名の経緯:
  - Gen(減×言)→ generator / generation との混同リスクで却下
  - Ori(折り)→ 一度採用したが、Rust の UI フレームワーク「Ori」との衝突が発覚し撤回
  - Oru(折る)→ crates.io で既存(Origami Linux の設定マネージャ)
  - Tatami(畳)→ crates.io / npm とも既存クレート・パッケージあり
  - Hida(襞)→ 両レジストリ空き・o200k 1トークンで次点候補として保留

## 1. コンセプトと要件

AI(LLM)がコードを書くことを第一に設計された新しいプログラミング言語を作る。

### 要件

- **ターゲット環境**
  - コマンドラインツールの開発に利用できる
  - モバイルネイティブアプリにも利用できる
  - Web 向けには wasm 対応する
- **相互運用性(FFI)**
  - 他のプログラミング言語でビルドしたライブラリをバイナリのまま利用できる
  - 逆に、この言語で書いたコードを他の言語から利用できる手段を何らかの形で提供する
- **文法**
  - トークンを節約できることを最優先とする
  - 人間も一応読んで理解できるようにする。**人間が書けることは求めない**

## 2. 実現可能性の評価

### 解決済みの領域(既存基盤に乗れる)

- **バックエンド**: LLVM(または MLIR)をバックエンドにすれば、ネイティブバイナリ(CLI・モバイル)と wasm は同じフロントエンドから出力できる。
- **FFI**: C ABI を共通言語にするのが定石。他言語バイナリの import も、この言語からの export も、Rust / Zig が実証済みのパターンをなぞれる。
- **モバイル**: 「C ABI の静的/動的ライブラリとして Kotlin / Swift から呼ぶ」形なら難度は低い。UI までこの言語で書くなら難度が桁違いに上がるため、スコープ判断が必要。

### リスク①: 学習データゼロ問題

LLM は訓練データにない言語を書くのが苦手。「AI が書く言語」なのに AI が書けない、というのが最大の矛盾点。

対策:

- (a) 文法を既存言語(Rust / TypeScript 系)の変形に留めて知識の転移を効かせる
- (b) コンパイラのエラーメッセージを LLM 向けに設計し、フィードバックループで修正させる前提にする
- (c) 文法リファレンス + few-shot をコンテキストに常駐させる運用を、言語仕様の一部とみなす

### リスク②: トークン節約が直感どおりに効かない

BPE トークナイザでは、頻出英単語(`function`, `return`)は 1 トークンだが、独自記号の組み合わせ(`fn⟨`, `»=`)は複数トークンに分解されがち。**「短い文字列 = 少ないトークン」は成り立たない。** 実測が設計の前提になる。

## 3. 検討手順(推奨順)

1. **「AI 寄り」の定義を分解する** — トークン効率、エラーの機械可読性、局所編集のしやすさ(diff が小さく済む文法)、曖昧性のなさ。優先順位を決める。
2. **トークン実測実験** — 既存言語のコード数百サンプルを各社トークナイザ(o200k, Claude 系など)で計測し、トークンがどこに消えているか分析する。実は識別子名とボイラープレートが大半で、記号選びより「宣言の省略」「型推論」「インポート自動化」の方が効くはず。
3. **紙上文法プロトタイプ** — 同じプログラムを新文法と既存言語で書き比べ、トークン数と LLM の生成成功率を測る。処理系を作る前にここで仮説検証する。
4. **意味論の決定** — GC か所有権か。AI に書かせるなら所有権エラー多発は避けたいので GC または参照カウントが無難。ただし wasm サイズと FFI の単純さに影響する。
5. **処理系の実装戦略** — 最初は自前 LLVM フロントエンドではなく、Zig か C へのトランスパイラが現実的。ネイティブ・wasm・クロスコンパイル・C FFI を全部既存ツールチェーンに丸投げでき、数週間で MVP に到達できる。
6. **FFI 設計** — ヘッダ自動生成(cbindgen 相当)と、C ヘッダからのバインディング自動生成。

## 4. 段階的進化計画

実現可能性を高めるため、段階的アプローチを採用する。各段階が「動く成果物」と「仮説検証」を兼ねる。

### Stage 1: 既存言語の「トークン節約方言」(数週間〜)

新言語をゼロから作らず、まず**母体言語へ機械的に展開できる短縮記法レイヤー**として始める。実体は単純なトランスパイラ(ほぼプリプロセッサ)。

これで一気に解決するもの:

- **学習データゼロ問題** → 母体言語の知識が転移する。LLM には「Rust の短縮記法」として少量のルール説明だけで書かせられる
- **ツールチェーン** → ネイティブ、wasm、クロスコンパイル、C ABI 双方向 FFI を母体言語のものを丸ごと流用
- **トークン節約仮説の実測** → 同一プログラムの方言版と素の母体言語版を比較すれば効果が数字で出る

**母体言語の候補**:

| 候補 | 評価 |
|---|---|
| **Rust(第一候補)** | LLM 習熟度が高く、cargo 一つで wasm・FFI・クロスコンパイルが揃う。所有権エラーの多発が懸念点だが、方言側で頻出パターンを型推論・自動 clone 等で吸収する余地あり |
| Zig | FFI とクロスコンパイルが最も素直だが、学習データが少なめ |
| Go | GC が欲しい場合の選択肢だが、wasm サイズと cgo の扱いにくさが要件と相性が悪い |

**ゲート条件**: トークン削減率が実測で意味のある水準(例: 30% 以上)に届き、LLM の生成成功率が素の Rust と同等以上。届かなければ文法を作り直すか前提を見直す — **処理系に投資する前に撤退判断できるのが段階化の最大の利点**。

### Stage 2: 独自意味論の導入(数ヶ月)

母体言語に 1 対 1 対応しない機能を少しずつ追加し、トランスパイラを本物のコンパイラフロントエンドに育てる。

- LLM 向けエラーメッセージ(構造化・修正提案つき)
- diff が小さく済む構文設計
- インポート自動解決

など「AI 寄り」の本体はここ。出力先は引き続き母体言語なので、バックエンドの心配は不要。

**ゲート条件**: 方言では表現できない価値(生成成功率や修正ループ回数の改善)が実証できること。

### Stage 3: 独立した処理系(その後)

独自 AST → C バックエンド or LLVM に移行し、母体言語から独立。C ABI は維持するので FFI 資産はそのまま。トランスパイル出力の遅さや母体言語の制約が実害になった時点で初めて着手する。

### Stage 4: エコシステム

モバイル UI バインディング、パッケージマネージャ、LSP など。Stage 3 までは「C ライブラリとして組み込む」でモバイル要件をカバーする。

## 5. MVP スコープ案

- **含める**: CLI 向けバイナリ生成、wasm 出力、C ABI 双方向 FFI、LLM 向けエラーメッセージ
- **外す**: モバイル UI(C ライブラリ組み込みで代替)、パッケージマネージャ、LSP、デバッガ

## 6. 次の一手

**手順 2 のトークン実測**から着手する。Rust コードの実サンプルを各社トークナイザで計測し、トークンがどこに消えているかを分析する。この結果で文法設計の方針がほぼ決まり、「トークン節約優先」という前提自体の検証にもなる。

最悪 Stage 1 で終わっても「Rust のトークン節約プリプロセッサ」という単体で有用な成果物が残る構成。
